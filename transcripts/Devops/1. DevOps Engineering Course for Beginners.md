## Introduction to DevOps

* DevOps is a **methodology** that helps engineering teams build products better by **continuously integrating user feedback**. 

* DevOps differs from traditional software development:
  
<img width="762" height="252" alt="image" src="https://github.com/user-attachments/assets/bfe25d23-d1b3-442b-ab74-9f1a154c2616" />

  * Traditional:
    * Software built like factory products.
    * Input: programming → Output: final product (e.g., CD).
   
 <img width="444" height="323" alt="image" src="https://github.com/user-attachments/assets/9e1f1b15-6bc0-4942-bc49-9dc2b0456dfe" />
     
  * Modern:
    * Continuous updates enabled by the internet.
    * No need for new versions (e.g., Facebook updates continuously).
    * Feedback is integrated into the same product.

## DevOps Lifecycle (Continuous Cycle)

<img width="509" height="257" alt="image" src="https://github.com/user-attachments/assets/e9cf6198-4449-40b5-bfbd-d1cda2d2cd19" />


* **Planning**

  * Define features to build.
  * Create specifications with the team.

* **Coding**

  * Developers implement features.

* **Building**

  * Convert source code into runnable artifacts:

    * Web: bundle into JavaScript.
    * Games: builds for Linux, Windows, browser.

* **Testing**

  * Automatic → Continuous Integration (CI).
  * Manual → Quality Assurance (QA).

* **Release**

  * Stakeholder approval.
  * Automated in Continuous Deployment.

* **Deployment**

  * Software delivered to users:

    * Website → public internet.
    * Mobile → App Store.
    * CD → physical distribution.

* **Operation**

  * Scaling infrastructure.
  * Managing servers and resources.
  * Handling architecture issues.

* **Monitoring**

  * Track user activity and system health.
  * Ensure system reliability.

* **Feedback Loop**

  * Use monitoring + user feedback to:

    * Fix bugs
    * Improve architecture
    * Build new features

* This cycle repeats continuously (e.g., Scrum cycles).

## Pull Request Automation

<img width="725" height="359" alt="image" src="https://github.com/user-attachments/assets/f66516e6-95ae-41ed-ac5b-b84e53c5f635" />

### Concept

* Developers share work via **pull requests (PRs)**.
* PRs are:

  * Atomic (self-contained)
  * Fully functional independently

### Goals

* Provide **fast feedback**
* Allow **same-day merge**
* Reduce bureaucracy

### Process

* Developer submits PR
* Goes through:

  * Automated checks
  * Code review
  * Stakeholder review

### Code Review

* Done by another developer:

  * Code style
  * Architecture
  * Scaling concerns
  * Subjective feedback 

### Stakeholder Review

* Designers and product managers:

  * UI/UX correctness
  * Placement
  * Responsiveness

### Automation Examples (What can you Automate?)

* Automated test execution
* Ephemeral environments
* Security scanning
* Reviewer notifications

### Goal as a DevOps Engineer

* Help Developers change proposals get reviewed and merged within 24 hours of when they are made.

### Key Benefit

* Developers don’t need to ask everyone before changes
* Passing tests + QA = assumed correctness

### Technologies

* GitHub
* GitLab
* BitBucket

## Deployment Automation

### Goals

* Automate deployment process
* Prevent downtime

### Key Concepts

* **One-step build process**
* **Canary deployments**

## Application Performance Management (APM)

### Purpose

* Ensure application health and performance

### Real-world Example

* Stack Overflow outage due to trailing spaces in a post

### Components

* **Metrics**

  * Request latency
  * Resource usage

* **Logging**

  * Track user actions
  * Map request → system components

* **Monitoring**

  * Detect anomalies
  * Auto-scale servers

* **Alerting**

  * Notify engineers
  * Trigger actions (rollback, fix)

## Testing Fundamentals

### Types of Tests (Coffee Maker Analogy)

* **Unit Tests**

  * Test individual components
  * Example: heater works

* **Integration Tests**

  * Test components together
  * Example: heater heats water

* **System (End-to-End) Tests**

  * Test full system
  * Example: coffee is brewed

* **Acceptance Tests**

  * User satisfaction
  * Example: usability, reliability

### Traditional Workflow

1. Plan

3. Test

### TDD Workflow

1. Plan
2. Write failing tests
3. Write code to pass tests

### Benefits

* Clarifies requirements

## Continuous Integration (CI)

### Definition

* Developers push changes frequently.
* Automated system runs tests on each change. 

### Benefits

* Faster development
* Safer changes
* Reduced bugs
* Handles legacy code confidently

### Workflow

* Create feature branch
* Push code
* CI runs tests
* Results shown in PR
* Merge if tests pass

### Scaling

* Enables team growth from 1 → 10 developers

---

### Example Workflow

* Install CI tool (e.g., LayerCI)
* Add configuration file
* Steps:

  * Install Docker & Docker Compose
  * Copy repo files
  * Build services
  * Start services
  * Run tests

### Example Tests (Cypress)

* Login test
* Message sending test
* UI validation

### Result

* PR shows:

  * Test status (✔ / ❌)
  * Confidence in changes

## Code Coverage

### Definition

* Measures how much code is tested

### Types

* **Line Coverage**

  * % of executed lines

* **Branch Coverage**

  * % of executed logical paths

### Line Types

* Syntax lines (not testable)
* Logic lines (have effects)
* Branch lines (control flow)

### Use Cases

* Large codebases
* Legacy systems
* Risk analysis

### Policies

* Code coverage must not decrease
* Assign test owners

### Trade-offs

* High coverage → stability
* But slower development

## Ephemeral Environments

### Definition

* Temporary environments per PR

### Purpose

* Allow **visual + functional review**

### Benefits

* Faster feedback
* No local setup needed
* Enables non-technical reviews

### Features

* Accessible via link
* Full application instance

### Challenges

* **Database state**

  * Must be:

    * Pre-populated
    * Secure (no PII)
    * Resettable
    * Schema-matched

* **Lifecycle**

  * When to create/delete

* **Cost**

  * Multiple environments increase cost

### Best Practices

* Tie lifecycle to PR
* Use hosted solutions (LayerCI, Heroku)

## Containers vs Virtual Machines

### Linux Responsibilities

* Memory (RAM)
* CPU
* Disk
* Devices (GPU, network)

### Problem

* Resource conflicts:

  * Same ports
  * Different dependencies

---

## Containers

* Isolate applications
* Each container:

  * Own file system
  * Own ports
* Uses **namespaces**

### Behavior

* Processes inside container:

  * Cannot see outside processes
  * Have isolated resources

---

## Virtual Machines (VMs)

* Emulate full hardware + OS
* Use **hypervisor**

### Characteristics

* Slower (10–20%)
* More storage (50–100% more)
* More memory usage

---

## Containers vs VMs

### Containers

* Lightweight
* Faster
* Share OS

### VMs

* Strong isolation
* Run different OS
* Better for untrusted code

## Key Takeaways

* DevOps = **continuous feedback loop**
* CI = **first and most important automation**
* Balance:

  * Speed vs stability
* Automation increases with product maturity
* Containers are default deployment choice
* Ephemeral environments are **next-gen code review**
